Attention 计算：自定义 kernel 对原版 vLLM attention kernel 的加速比

"全量"指每个 query 对所有 key 计算；"稀疏"指按每个注意力头只计算贡献最大的 64×64 块，保留 95% 的注意力质量，实际参与计算的块在 64K/128K/256K 输入下占 50%/48%/44%。

数据表
  • FP8 kernel 用 8 位浮点（e4m3）做 attention 的矩阵乘，速度是 BF16 的约 2 倍；"流水优化版"进一步用 TMA 异步加载和多级流水，把张量核心的利用率从 75% 提到 84%。
  • 稀疏带来的加速与参与计算的块占比成反比；块选择本身的开销（每层约 1～2 ms）未计入本图，已计入下方的端到端结果。

端到端：首 token 时间对原版 vLLM 的加速比

前四个方案逐步叠加：① MLP 的 gate/SwiGLU 融合 → ② 稀疏 attention（BF16 kernel）→ ③ 换 FP8 attention kernel → ④ FP8 kernel 流水优化版（方案 A）。方案 B 是稀疏 BF16 attention 加 FP8 矩阵乘（GEMM），方案 C 是全 FP8（FP8 attention 加 FP8 GEMM）。每个数据点为预热后两次测量的平均。

数据表（含两条请求并发）
  • attention 在首 token 时间中的占比随输入长度增长（64K 约 22%，256K 约 55%），其余主要是矩阵乘。所以 attention kernel 提速 3 倍在 64K 只换来约 20% 的端到端收益，而 FP8 矩阵乘的收益更大。
  • 输出质量：把原版 BF16 生成的 256 个 token 逐个交给各方案打分，三个方案的平均负对数似然差都在 0.01 以内，首选 token 一致率 97%～99%，藏在长文档里的信息全部检索正确。误差主要来自 FP8 矩阵乘，FP8 attention 几乎不增加误差。
  • 两条 256K 请求并发时原版需要 172 s，是因为原版的显存放不下两条 256K 的上下文，第二条要排队；该行以融合版为对照。
  • prefill 每步处理 12032 个 token（而不是 8192）可以让 attention kernel 的线程块数恰好填满 GPU，全 FP8 方案的首 token 时间再快约 2%。
